# P8 튜닝 평가 — 대표 실패·성공 5건 손정독

자동 분류(`failure_layer`)가 알려주는 것은 분포뿐이다. 표 하나로는 원인을
알 수 없다는 설계서 6.4의 지적대로, 아래 5건은 `runs.jsonl`의 실제
`trace`와 `data/docs/*.md` 원문을 직접 대조해 읽었다.

## Q01 — 동방신기는 어느 기획사에 소속되어 있는가?

| 항목 | 내용 |
| --- | --- |
| 질문 | 동방신기는 어느 기획사에 소속되어 있는가? |
| 기대 경로 | 동방신기 -[SIGNED_TO]-> SM 엔터테인먼트 (1홉) |
| 실제로 탄 경로 | 동방신기 -[SIGNED_TO]-> Red 프로덕션, 동방신기 -[SIGNED_TO]-> SM 엔터테인먼트 (둘 다 hop 1에서 발견) |
| 원문 한 줄 | 그래프에 `동방신기 SIGNED_TO Red 프로덕션`과 `동방신기 SIGNED_TO SM 엔터테인먼트`가 둘 다 실재한다 — 추출 오류가 아니라 그래프에 두 소속사 사실이 모두 들어 있다 |
| 어디서 왜 깨졌는가 | 자동 분류: `generation`(idx.exact=1, triple_recall=1인데 심판이 0점). 손으로 읽은 원인: 에이전트가 근거에 있는 사실을 정직하게 전부 답했는데(환각 아님), `answer_type: single`+`answer_aliases`가 "SM 엔터테인먼트" 하나만 정답으로 인정해 심판이 "정답 외 사실을 덧붙였다"고 0점을 준 것으로 보인다 |
| 고쳤는가 | 안 고쳤다. 이건 파이프라인 버그가 아니라 골든셋 설계의 한계다 — "정답과 실질적으로 동일하면 1.0"이라는 judging_rules.md 기준이 "정답을 포함하되 추가 사실도 맞다면?"을 명시하지 않는다. Q01의 실제 표기(예: 데뷔 당시 레이블)를 원문에서 확인해 `answer_aliases`나 부분점수 규칙을 보완할지는 REPORT.md에 한계로 남긴다 |

## Q03 — 신승훈의 데뷔곡 《미소 속에 비친 그대》는 누가 작곡하였는가?

| 항목 | 내용 |
| --- | --- |
| 질문 | 신승훈의 데뷔곡 《미소 속에 비친 그대》는 누가 작곡하였는가? |
| 기대 경로 | 신승훈 -[WROTE]-> 미소 속에 비친 그대 (1홉) |
| 실제로 탄 경로 | 근거 부족으로 기권(코드층 게이트, `미확보 관계: WROTE`) |
| 원문 한 줄 | `신승훈.md`: "데뷔곡인《미소 속에 비친 그대》를 포함한 1집에 수록된 7곡이... 바로 이 때 작곡한 곡들이다" — 원문에는 있지만 그래프에 WROTE 간선으로 추출되지 않았다(직접 확인: `output/graph.json`에 해당 (h,r,t) 없음) |
| 어디서 왜 깨졌는가 | 자동 분류: `index`(idx.exact=0). 손으로 읽은 원인과 일치 — 그래프에 사실 자체가 없다. LLM 추출이 "데뷔곡인... 바로 이 때 작곡한 곡들이다"라는 간접적 서술(WROTE를 명시적으로 말하지 않고 앞뒤 문맥으로 유추해야 함)에서 명시적 WROTE 관계를 뽑지 못했다 |
| 고쳤는가 | 안 고쳤다. 재추출(3번째)까지 이미 진행했고, 이 정도의 간접 서술을 규칙 없이 LLM이 항상 잡아내길 기대하긴 어렵다 — 실제 LLM 추출 재현율의 한계로 기록한다 |

## Q08 — 서태지와 아이들의 1집 《Seotaiji and Boys》에 수록된 곡 중 하나는?

| 항목 | 내용 |
| --- | --- |
| 질문 | 서태지와 아이들의 1집 《Seotaiji and Boys》에 수록된 곡 중 하나는? |
| 기대 경로 | 서태지와 아이들 -[RELEASED]-> Seotaiji and Boys -[CONTAINS]-> 난 알아요 (2홉) |
| 실제로 탄 경로 | 근거 부족으로 기권(`미확보 관계: CONTAINS`). trace에 `God -[RELEASED in]-> 1집`이 섞여 있다 |
| 원문 한 줄 | 시드 탐색이 `album:1집`을 세 번째 시드로 잘못 잡았다 — "1집"이 여러 그룹의 앨범에 공통으로 쓰이는 일반적인 제목이라, 질문의 "1집"이 부분매칭으로 God의 "1집" 노드와 엉뚱하게 정규화 일치했다 |
| 어디서 왜 깨졌는가 | 자동 분류: `routing`(route_actual이 기대와 다름 — 이 문항은 `path`를 기대했는데 규칙이 `local`로 판정, "수록" 큐 하나만 매칭돼서다). 손으로 읽은 원인은 다르다 — 진짜 문제는 라우팅이 아니라 **시드 오염**이다: "1집"처럼 여러 앨범이 공유하는 일반적 제목이 `find_seeds()`의 부분매칭에서 엉뚱한 앨범과 매치된다 |
| 고쳤는가 | 안 고쳤다. `find_seeds()`의 부분매칭이 너무 짧고 흔한 제목(2자 이내 또는 다수 문서에 공통인 제목)을 걸러내도록 만드는 게 근본 해법일 텐데, 이번 P8 실행 이후에 발견해 추가 재실행(과금) 없이는 검증할 수 없다. Task 20 완료 후 후속 작업으로 REPORT.md 한계에 기록하고 남긴다 |

## Q10 — 지드래곤이 소속된 그룹이 수상한 시상식 두 곳은?

| 항목 | 내용 |
| --- | --- |
| 질문 | 지드래곤이 소속된 그룹이 수상한 시상식 두 곳은? |
| 기대 경로 | 지드래곤 -[MEMBER_OF]-> 빅뱅 -[WON]-> 골든디스크, 서울가요대상 (2홉) |
| 최초 실행 결과 | 근거 부족으로 기권(`미확보 관계: WON`) — `지드래곤 -[MEMBER_OF]-> 빅뱅` 간선 자체가 trace에 전혀 없었다 |
| 원문 한 줄 | `graph.json`에 `지드래곤 -MEMBER_OF-> 빅뱅` 간선이 실재한다(직접 확인). 그런데 지드래곤의 전체 out-degree가 9인데 `per_node_out=8`이 그래프 삽입 순서 그대로 앞 8개만 남기고 있었다 — MEMBER_OF가 정확히 9번째였다 |
| 어디서 왜 깨졌는가 | 자동 분류: `retrieval`(triple_recall<1). 손으로 읽은 원인이 자동 분류보다 훨씬 구체적이다 — 그래프에도 있고(색인 통과) 필요한 관계로도 잡혔는데(라우팅 통과) 예산 절단 순서 버그로 사라졌다. "소속"이 SIGNED_TO로만 매핑되던 부수 원인도 같이 찾았다(위 "실행 중 발견한 버그 둘" 참고) |
| 고쳤는가 | **부분적으로 고쳤다, 그리고 남은 한계를 발견했다.** 세 가지를 TDD로 고쳤다: ① `per_node_out`을 점수 계산 후 상위 N개로 자르도록, ② `CUE_TO_RELATIONS`의 "소속된 그룹"을 MEMBER_OF로 분기하도록, ③ `run_retrieval()`이 1홉째에 `gap_rels`를 빈 리스트로 시작해 필수 관계 가산점(1.3배)이 1홉째엔 전혀 적용되지 않던 버그(모두 187개 테스트 통과, 커밋 완료). 이 세 수정을 전부 적용한 뒤 LLM 비용 없이 `run_retrieval()`만 다시 돌려 실제로 검증했는데, **그래도 MEMBER_OF가 여전히 빠진다.** 원인: 빅뱅 자체가 차수 87의 허브급 노드라, 1.3배 가산점을 받아도 이 시스템의 허브 감점(`degree_penalty = 1/(1+차수^0.5)`)을 못 이긴다 — SIGNED_TO(허브 아님, 가산점 없음)보다도 점수가 낮아 `per_node_out=8` 컷오프 밖으로 밀린다. 이건 버그가 아니라 Q15와 동일한 설계상 트레이드오프다(아래 참고): "가짜 다리를 막는다"는 목적과 "빅뱅처럼 진짜 정당한 목적지가 마침 허브인 경우"가 충돌한다. 추가로 고치려면 "필수 관계는 `per_node_out`/감점에서 면제한다"는 새 규칙을 설계에 넣어야 하는데, 사용자와 상의한 결과 지금은 고치지 않고 한계로만 기록하기로 했다. `output/eval.json`의 수치는 이 세 수정 *이전* 실행 결과다 |

## Q15 — 서태지와 아이들의 멤버 중 대형 기획사를 설립한 사람이 세운 회사에 소속된 3인조 보이 그룹은? (세대 교차)

| 항목 | 내용 |
| --- | --- |
| 질문 | 서태지와 아이들의 멤버 중 대형 기획사를 설립한 사람이 세운 회사에 소속된 3인조 보이 그룹은? |
| 기대 경로 | 양현석 -[MEMBER_OF, in]-> 서태지와 아이들, 양현석 -[FOUNDED]-> YG 엔터테인먼트, 빅뱅 -[SIGNED_TO, in]-> YG 엔터테인먼트 (3홉) |
| 실제로 탄 경로 | 근거 부족으로 기권. P6 게이트에서 이미 확인한 것과 같은 원인 — YG 엔터테인먼트가 실제 허브(차수>25)라 시드가 아닌 한 경유가 금지된다 |
| 원문 한 줄 | `양현석 FOUNDED YG 엔터테인먼트`, `빅뱅 SIGNED_TO YG 엔터테인먼트` 둘 다 그래프에 실재하지만, YG는 다른 소속 아티스트가 많아 `hub_degree_threshold=25`를 넘는다 |
| 어디서 왜 깨졌는가 | 자동 분류: `retrieval`. 손으로 읽어도 같은 결론 — 허브 회피가 설계대로 작동해 이 정당한 3홉 체인까지 막았다. "가짜 다리를 막는다"는 목적과 "진짜 체인을 놓치지 않는다"는 목적이 이 문항에서 정면으로 충돌한다 |
| 고쳤는가 | 안 고쳤다. Task 14의 P7 스윕이 `hub_degree_threshold=None`(차단 없음)에서 근소하게 더 나은 재현율을 보였지만 스윕 자체가 근사치라 확정하지 않기로 했었다 — 이번 실측(Q15가 정확히 이 이유로 실패)이 그 스윕 신호를 뒷받침하는 추가 증거다. 임계값을 25보다 높이는 것(예: 40)을 REPORT.md에서 권고 사항으로 남긴다. **Q10도 같은 원인으로 다시 걸렸다** — Q10 재검증 중 빅뱅(차수 87)으로 가는 필수 간선이 허브 감점 때문에 탈락하는 걸 확인했다(위 Q10 항목 참고). 같은 트레이드오프가 서로 다른 두 문항에서 독립적으로 재현된 것이라, "필수 관계는 허브 감점/예산에서 면제한다"는 규칙 추가가 다음 튜닝 라운드의 확실한 후보다 |

## 요약

| 문항 | 자동 분류 | 손으로 읽은 실제 원인 | 고쳤는가 |
| --- | --- | --- | --- |
| Q01 | generation | 정답 포함 + 추가 사실 → 심판이 엄격하게 0점. 채점 기준의 한계 | 아니오(설계 한계로 기록) |
| Q03 | index | LLM이 간접 서술에서 WROTE를 못 뽑음. 추출 재현율 한계 | 아니오(실측 한계로 기록) |
| Q08 | routing | 시드 탐색이 "1집" 같은 흔한 제목에서 엉뚱한 앨범과 매치 | 아니오(후속 과제로 기록) |
| Q10 | retrieval | `per_node_out` 절단 순서 + '소속' 중의성 + `gap_rels` 1홉째 미시딩 (3개 버그) + 빅뱅 자체의 허브 감점 (구조적 한계) | 버그 3개는 **고쳤다**(TDD+커밋). 마지막 원인(허브 감점)은 Q15와 같은 구조적 트레이드오프라 **고치지 않고 기록만** |
| Q15 | retrieval | 허브 회피가 정당한 3홉 체인까지 막음(설계상 트레이드오프, Q10과 동일 원인) | 아니오(임계값/필수관계 면제 권고로 기록) |

자동 분류와 손으로 읽은 원인이 어긋난 사례(Q08: routing으로 분류됐지만 진짜 원인은 시드 오염, Q15: retrieval로 분류됐지만 원인은 허브 회피의 의도된 트레이드오프)가 나왔다 — 이것이 설계서 6.4가 말한 "가장 값진 기록"이다. 자동 분류 규칙 자체(`classify_failure`)가 라우팅/시드/색인/검색을 완벽히 가르지 못한다는 뜻이며, 6계층 분류는 진단의 출발점이지 최종 답이 아니다.

**중요**: 이 표의 수치(`output/eval.json`)는 아래 네 가지 코드 수정 *이전*의 실행 결과다 — `path_prefix_recall` 홉 그룹핑, `per_node_out` 채점-후-절단, "소속" 중의성 분기, `gap_rels` 1홉째 시딩. 네 개 모두 TDD로 고치고 커밋했지만(187 tests passing), 고친 코드로 15문항을 LLM 답변·심판까지 다시 돌리려면 추가 과금이 필요해 재실행 여부는 사용자 확인 대상으로 남긴다. Q10 하나는 LLM 비용 없이 `run_retrieval()` 재실행으로 검증했고, 그 결과 다섯 번째 원인(빅뱅의 허브 감점)이 구조적 한계로 남아 있음을 확인했다(사용자와 합의해 고치지 않고 기록만 함) — 나머지 14문항은 개별 재검증을 하지 않았으므로 다른 개선/악화가 있을 수 있다.
